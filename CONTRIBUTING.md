# Contributing to ShieldClaw

## Dev setup

```bash
# 1. Clone and enter the repo
git clone git@github.com:blondres04/shieldclaw.git
cd shieldclaw

# 2. Create a virtual environment (Python 3.11+ required)
python3.11 -m venv .venv
source .venv/bin/activate          # Linux / macOS
# .\.venv\Scripts\Activate.ps1    # Windows PowerShell

# 3. Install the package and all dev tools
pip install -r shield-claw/requirements.txt \
            -r shield-claw/requirements-dev.txt \
            -e shield-claw/

# 4. Install pre-commit hooks (runs on every git commit automatically)
pre-commit install
```

---

## Running tests

```bash
cd shield-claw

# Unit tests only (no Docker required) — what CI and pre-commit run
pytest -m "not integration" --no-cov -q

# Architecture isolation tests only (fastest gate)
pytest tests/test_architecture.py -q

# Full suite including integration tests (Docker daemon must be running)
pytest -m integration -q

# All checks at once (ruff format, ruff lint, mypy, pytest unit)
pre-commit run --all-files
```

## Branch naming convention

```
pivot/sast-verifier          ← v0.2 pivot trunk (never commit to main directly)
phase-N/short-slug           ← phase feature branch (cut from pivot trunk)
fix/description              ← bug fix (cut from pivot trunk or phase branch)
```

Example: `feat/semgrep-ingest`, `fix/sarif-parser-empty-results`.

All phase branches are squash-merged back to `pivot/sast-verifier` when
the phase's verification milestone passes.

## Commit conventions

Format: `type(scope): subject`  
Subject line ≤ 72 characters, imperative mood, no trailing period.  
Body wraps at 72 characters.  
No co-author trailers, no "Generated by..." lines, no emoji in subjects.

### Types

| Type | When to use |
|------|-------------|
| `feat(scope)` | New feature or package |
| `fix(scope)` | Bug fix |
| `refactor(scope)` | Code restructure without behaviour change |
| `test(scope)` | Add or update tests |
| `chore` | Build config, CI, tooling |
| `docs` | Documentation only |
| `ci` | CI/CD pipeline changes |

### Referencing issues

- In commit body: `Refs #N` (progress) or `Closes #N` (completion).
- In the squash-merge commit body: `Closes #N` for the phase issue.

### Example

```
feat(ingest): parse SARIF 2.1 result objects into Finding dataclasses

Accept both file-path and stream inputs. Results with no physicalLocation
are dropped with a warning; partial parses still return the valid subset.

Refs #15
```

## Module isolation rule

ShieldClaw enforces strict package boundaries as an architectural invariant:

- The packages `context`, `intelligence`, `sandbox`, `reporting`, `ingest`,
  `triage`, `scoring`, `approval`, `observer`, `remediation`, and
  `persistence` **must not import from each other**.
- Only `orchestrator.py` and `__main__.py` may cross package boundaries.
- `models.py` and `exceptions.py` carry **zero** internal `shieldclaw.*`
  imports.
- All inter-stage data is passed as **immutable frozen dataclasses** defined
  in `models.py`.
- All custom exceptions extend `ShieldClawError` and live in `exceptions.py`.

This constraint is enforced by `tests/test_architecture.py` via static AST
analysis on every test run and in the pre-commit `pytest-unit` hook.
**Update `test_architecture.py` whenever you add a new package.**

See [ADR-001](shield-claw/docs/adrs/001-module-isolation.md) for the rationale.
